# Contract — The swimmer's request

Phase 1 of the plan. The guarantees this feature promises, and the **exact body** of every new
call to the server.

The second part is here because of the most expensive lesson of feature 006: the client sent
the guardian's data flat and the server unpacked it nested. Ten tests of the guardian path were
green, because **doubles implement the interface, not the wire**. Every new call carries its
body written here and a test that compares it against the server source.

Guarantees are numbered `P1…Pn` ("petición") so they can be cited from `tasks.md` and from
test names.

---

## The list of questions

**P1** — The list asks exactly six things and no more: stroke, event, competition date,
available days, session duration, pool length. Adding a seventh is a change to this contract,
not an implementation detail.

**P2** — Stroke and event arrive **pre-filled from the swimmer's record**. The swimmer may
change them for this request without changing their record.

**P3** — Nothing in the list requires writing free text. The whole list is answerable by
tapping.

**P4** — «No lo sé» is a valid answer to the competition date, and it does not block sending.

**P5** — The list is answerable with no connection, and what was answered survives closing the
app.

**P6** — The app never asks the swimmer for their category, their ATR phase, their accentuated
component, their technical diagnosis, or their discomfort. Each of those five absences is
checkable by searching the swimmer's screens for the question.

**P7** — A swimmer with no record, or whose record has no category or no target event, is told
their coach has to complete it. They are not shown a list that cannot lead to a draft.

---

## What leaves the device

**P8** — A request leaves through the outbox and the consent gate that features 003 and 004
already built. **No third path off the device is created.**

**P9** — A minor without valid consent sends nothing. The app says the guardian's authorisation
is missing and does not say the request was sent.

**P10** — What was held for lack of consent leaves as soon as consent exists, without being
written again.

**P11** — A swimmer can only write a request that is their own. Verified against the rules, not
only in the interface.

**P12** — A swimmer with an unanswered request cannot send another. Verified against the rules.

**P13** — The device never writes `enviadaEn`, `estado`, `respondidaEn` or `planId`. Verified
field by field against the rules: a client that can write its own state can approve its own
request.

---

## The draft

**P14** — The draft is generated by the deterministic engine of feature 002. No language model
takes part, at any point, in any field.

**P15** — The draft is generated **on the coach's device when he opens the request**. It never
exists on the swimmer's device. This is what makes P16 a fact rather than a promise the
interface makes.

**P16** — The swimmer cannot see the draft's contents before approval. What they see is the
state of their request.

**P17** — The draft is born in state `borrador`, and carries: `OrigenPlan.automatico`, the id
of the request it came from, and the methodology version it was built under.

**P18** — Generating a draft delivers, publishes and assigns nothing. A request that is
generated and left alone changes nothing for any swimmer.

**P19** — The draft passes the section 16 audit before it can be approved, and the coach sees
which criteria it meets and which it does not — the same audit as a plan of his own, not a
lighter one.

**P20** — Two generations from the same stored request produce the same draft. Verified by
generating twice and comparing, not by comparing once against a fixture: a fixture would hide
an input read from the clock.

---

## The derived phase

**P21** — When the category uses ATR, the phase is derived by counting back from the
competition date: 1-15 days → Realización, 16-43 → Transformación, 44 or more → Acumulación.

**P22** — When the category does not use ATR, no phase is set. The engine forbids one there,
and the draft says so rather than leaving it blank.

**P23** — A competition date that is today or in the past is treated as **no date**. The app
does not derive a phase from a competition that has happened.

**P24** — With no usable date and a category that uses ATR, **no draft is generated**. The
request reaches the queue with the phase pending for the coach to set.

**P25** — The accentuated component is derived from the phase, and the result passes the
coherence check the engine already performs between phase and component. By construction, not
by luck.

**P26** — The draft shows which phase was derived and why, in days until the competition, and
the coach changes it in one tap.

---

## The coach's queue

**P27** — The coach sees who asked, when, what they answered, and the draft.

**P28** — The coach corrects the draft with the same editor and the same audit as his own
plans.

**P29** — A rejection without a written reason is impossible. Not discouraged: impossible.

**P30** — The swimmer reads the reason their coach wrote, as he wrote it.

**P31** — Only the coach moves a request's state. Nothing moves it by elapsed time or by any
other automatic rule.

**P32** — With no connection, the queue shows what is in the cache and says the latest may be
missing. It does not show an empty queue that reads as "no requests".

---

## Discomfort

**P33** — The queue shows the discomfort the swimmer already reported inside the recent window,
**with its dates**.

**P34** — When the window holds none, the queue says so explicitly. A blank space reads as
"nothing hurts".

**P35** — Discomfort does not modify the generated plan. In any field, by any path.

**P36** — This feature writes nothing about discomfort anywhere. Verified by checking that no
write touches a discomfort field, not by inspecting the screen.

---

## Erasure

**P37** — Erasing a swimmer's data (feature 007) takes their request and its history with it.
Verified against the server, with the consent record surviving as it already does.

## The exact body of the new server calls

### `cerrarPeticion` — the coach answers

Called when the coach approves or rejects. The state is the server's to write, which is why
this is a call and not a client write (P13).

**Request body sent by the client**:

```json
{
  "nadadorId": "n-ana",
  "decision": "aprobada",
  "planId": "p-20261102-1",
  "motivo": null
}
```

```json
{
  "nadadorId": "n-ana",
  "decision": "rechazada",
  "planId": null,
  "motivo": "Pediste cinco días y en Precompetitivo son tres. Te armo uno de tres."
}
```

**Flat, not nested.** `decision` is exactly `"aprobada"` or `"rechazada"`; any other value is
rejected by the server. `motivo` is required and non-empty when `decision` is `"rechazada"`,
and must be null otherwise. `planId` is required when `decision` is `"aprobada"`.

**Response body**:

```json
{
  "estado": "aprobada",
  "respondidaEn": "2026-11-02T14:42:10.000Z",
  "archivadaEn": "peticionesDePlan/n-ana/historial/2026-11-02T14-30-00"
}
```

**P38** — The server refuses this call from anyone who is not the coach, and refuses a
`rechazada` with no reason. Both verified against the emulator with negative controls.

**P39** — A Dart test reads the TypeScript source of this call and compares the field names
against the body written above. The doubles implement the interface; this test implements the
wire.

---

## What this contract does not promise

- No plan longer than one microcycle: that is feature 009
- No push notification that a request arrived or was answered
- No club competition calendar
- No withdrawal of a sent request by the swimmer
- No automatic suggestion of any kind about a discomfort
