# Implementation Plan: The swimmer's request

**Branch**: `008-swimmer-request` | **Date**: 2026-11-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/008-swimmer-request/spec.md`

## Summary

A swimmer answers six questions they can actually answer, and the coach gets a draft he did not
have to type. The draft is generated by the deterministic engine of feature 002 **on the
coach's device when he opens the request**, which is what makes "the swimmer cannot see it
before the signature" a fact rather than something the interface says. Nothing reaches a
swimmer without his signature, a rejection is impossible without a written reason, and the
ATR phase the app derives is shown with its reason and changeable in one tap.

Three decisions carry the feature, and all three came out of reading what already exists:

1. **Only five of the engine's eleven inputs are the swimmer's to give.** The rest is on their
   record, read from their sessions, or the coach's judgement.
2. **The draft is generated on the coach's side**, so it never exists on the swimmer's phone.
3. **The request document is named after the swimmer**, so "one open request at a time" is a
   rule the server enforces rather than a habit the screen keeps.

## Technical Context

**Language/Version**: Dart 3.12.2 / Flutter 3.44.2. Server: TypeScript on Node 22, Firebase
Functions v2.

**Primary Dependencies**: no new ones. `cloud_firestore`, `firebase_auth`, `cloud_functions`,
`provider`, `shared_preferences` are all already in `pubspec.yaml`. The generator, the audit,
the consent gate and the outbox all exist.

**Storage**: Firestore. One new collection, `peticionesDePlan`, with a `historial`
subcollection. `shared_preferences` for the half-answered list and the outbox, through the
existing `AlmacenLocal`.

**Testing**: `flutter test` for domain and widgets, `@firebase/rules-unit-testing` against the
emulator for the access rules, `node --test` against the emulator for the server, and one
source-level contract test that reads the TypeScript and compares field names.

**Target Platform**: Flutter web (PWA) and Android. The coach works on either; the swimmer
mostly on a phone.

**Project Type**: single Flutter app plus Firebase backend, as the previous seven features.

**Performance Goals**: generating a draft on the coach's device is not perceptibly slower than
his own generator today, which is the same engine with the same inputs.

**Constraints**: the list is answerable offline and survives closing the app. The queue reads
from the cache when there is no connection and says the latest may be missing. No language
model takes part in any field of a generated plan.

**Scale/Scope**: one coach, a few dozen swimmers, at most one open request each. Six new domain
types, one new screen for the swimmer, one new section inside the coach's `Generar`, one new
server call.

**Structure Decision**: the layout the previous seven features established — pure domain under
`lib/dominio`, Firebase under `lib/datos`, screens under `lib/ui`, with the boundary tests
already in place enforcing that `lib/dominio` imports neither Flutter nor Firebase, that
`firebase_auth` appears only in `sesion_firebase.dart`, and that `cloud_functions` appears only
in `operaciones.dart`.

Two placements are worth saying out loud:

- **The derivation goes in the domain, not in the data layer.** It is a training rule. Putting
  it next to the Firestore code would make it unreachable from `flutter test` without a fake
  database, and principle III wants it tested with no infrastructure at all.
- **The queue goes inside the coach's existing `Generar`**, not in a sixth destination. The
  five destinations and their labels are locked by feature 007, including the lock that
  measures whether the labels fit at 320 px.

## Build order

The order is not negotiable in two places, and both are about not writing something before the
thing that guards it exists.

1. **The derivation and its tests first.** It is the only new training rule, it is pure, and it
   needs nothing else to exist. Its tests are written before it, including the boundary days
   (15/16, 43/44), the past date, and the category without ATR — each with a negative control.
2. **The access rules before the screens that write.** P11, P12 and P13 are the guarantees that
   stop one swimmer writing another's request and stop any client writing its own state. They
   get rules and negative controls before there is a screen that sends anything.
3. Then the domain types, the repository interface and the Firestore implementation.
4. Then the swimmer's list and the state screen.
5. Then the coach's queue, which is where the generation happens.
6. Then the server call that closes a request, with its wire test against the TypeScript source.
7. The seed last, because it needs the shapes to exist, and it is what makes the quickstart
   walkable.

## Complexity Tracking

> No constitution violations to justify. This section stays empty on purpose.

One thing that looks like complexity and is not: **generating the draft on demand, twice, for
the same request**. It costs a second generation and buys a guarantee — the draft never exists
where the swimmer could read it. The alternative, generating once on the swimmer's phone and
hiding it, is cheaper to build and makes FR-013 a decoration.
